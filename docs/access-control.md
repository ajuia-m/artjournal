# JWT, роли и серверная матрица доступа

Документ фиксирует первый рабочий контур аутентификации и авторизации Art
Journal. Его граница — пользователи, школы, членства и назначения
преподавателей. Предметные endpoints журнала будут подключать те же policy
functions и DRF permissions по мере появления.

## Модель доступа

`User` является глобальной учётной записью. Доступ к данным появляется только
через активный `Membership` конкретной школы:

- один пользователь может состоять в нескольких школах;
- в одной школе у пользователя не более одного членства;
- роль хранится в членстве, а не в `User`;
- поддерживаются роли `admin` и `teacher`;
- неактивный пользователь или неактивное членство не дают доступа;
- школа должна сохранять хотя бы одного активного администратора с активной
  учётной записью.

`TeachingAssignment` ограничивает преподавателя группой и, опционально,
дисциплиной:

- `subject = null` разрешает работу со всей группой;
- указанная дисциплина разрешает только её журнал;
- дисциплина должна быть назначена группе;
- членство, группа и дисциплина должны принадлежать одной школе;
- широкое назначение на группу нельзя смешивать с назначениями отдельных
  дисциплин той же группы.

## Матрица

| Действие | `admin` | `teacher` |
|---|:---:|:---:|
| Просматривать школу | Да | Да |
| Менять настройки школы | Да | Нет |
| Управлять членствами и ролями | Да | Нет |
| Управлять учебной структурой | Да | Нет |
| Запускать будущий серверный импорт | Да | Нет |
| Просматривать оплаты | Да | Нет |
| Менять оплаты | Да | Нет |
| Просматривать назначенную группу | Да, все группы | Да |
| Менять журнал назначенной группы | Да, все группы | Да |
| Работать с неназначенной группой/дисциплиной | Да | Нет |

Роль `teacher` не получает общешкольное право на журнал: проверяется конкретная
группа, а при наличии дисциплины — и конкретное назначение. Django
`superuser` имеет аварийный доступ ко всем школам, но не является заменой
обычному членству администратора.

## JWT

API использует `djangorestframework-simplejwt`:

- access token: 15 минут;
- refresh token: 7 дней;
- refresh token ротируется при обновлении;
- использованный или явно отозванный refresh token попадает в blacklist;
- заголовок защищённых запросов: `Authorization: Bearer <access>`;
- в payload хранится стабильный UUID пользователя.

Роль, школа и назначения намеренно не входят в JWT. На каждом запросе сервер
читает текущее состояние из PostgreSQL. Это немного дороже stateless-проверки,
зато смена роли, деактивация членства или отзыв назначения действуют сразу и
не оставляют старые права до истечения токена.

Для production `JWT_SIGNING_KEY` должен быть длинным случайным секретом,
отличным от `DJANGO_SECRET_KEY`. Токены передаются только по HTTPS и не должны
появляться в URL, логах, issue или CI artifacts.

## API

| Метод и путь | Назначение |
|---|---|
| `POST /api/v1/auth/token/` | вход по username/password |
| `POST /api/v1/auth/token/refresh/` | ротация refresh и выдача access |
| `POST /api/v1/auth/token/logout/` | blacklist переданного refresh |
| `GET /api/v1/auth/me/` | пользователь, активные членства и назначения |
| `GET /api/v1/schools/` | школы текущего пользователя |
| `GET /api/v1/schools/{schoolId}/` | школа при наличии активного членства |
| `GET/POST /api/v1/schools/{schoolId}/memberships/` | список/создание членств |
| `GET/PATCH/DELETE /api/v1/schools/{schoolId}/memberships/{id}/` | изменение членства |
| `GET/POST /api/v1/schools/{schoolId}/teaching-assignments/` | список/создание назначений |
| `GET/PUT/PATCH/DELETE /api/v1/schools/{schoolId}/teaching-assignments/{id}/` | изменение назначения |

Endpoints членств и назначений доступны только `admin` соответствующей школы.
Объект из другой школы не может быть получен через вложенный URL.

## Инвариант последнего администратора

Изменение и удаление членств выполняются транзакционным сервисом с блокировкой
строки школы. Последнего доступного администратора нельзя:

- перевести в `teacher`;
- деактивировать;
- удалить.

Связанный `User` защищён от удаления на уровне внешнего ключа. В Django Admin
пользователь и школа существующего членства неизменяемы, удаление членств
выключено, смена роли проходит через тот же сервис, а деактивация последней
доступной учётной записи администратора отклоняется формой пользователя.

Первое административное членство является bootstrap-операцией: его создаёт
Django `superuser` через `/admin/` после создания школы.

## Подключение к предметным API

Policy layer находится в `apps.schools.access` и не зависит от HTTP.
`HasSchoolAction` и `HasGroupAction` по умолчанию запрещают запрос, если view
не объявил нужное действие или resolver объекта. Новые endpoints должны:

1. требовать `IsAuthenticated`;
2. объявлять конкретный `SchoolAction` или `GroupAction`;
3. извлекать школу, группу и при необходимости дисциплину из серверных данных;
4. ограничивать queryset доступной школой до получения объекта;
5. не доверять `schoolId`, роли или списку групп, присланным клиентом.

## Известные ограничения

- Android-клиент ещё не получает и не хранит JWT.
- Нет регистрации, подтверждения email, восстановления пароля и MFA.
- Нет публичного endpoint импорта; management-команда остаётся локальной.
- Встроенный DRF throttle использует текущий cache backend. Для нескольких
  экземпляров приложения нужен общий Redis и дополнительный rate limit на
  reverse proxy/API gateway.
- Предметные CRUD endpoints ещё не созданы, поэтому групповые policy functions
  пока проверяются unit-тестами и предназначены для следующих вертикальных
  срезов.
