# Формат полной резервной копии JSON v1

JSON v1 — переносимый снимок локальной Room-базы Art Journal. Его основная
задача — сохранить данные до перехода на backend и дать серверному импортёру
однозначно определить структуру файла.

Машиночитаемый контракт:

- [JSON Schema v1](schemas/artjournal-backup-v1.schema.json);
- [анонимизированный полный пример](examples/artjournal-backup-v1.example.json);
- [правила преобразования в серверную модель](server-data-model.md).

Backend содержит идентичную runtime-копию схемы в
`backend/apps/imports/schemas/`; отдельный тест не позволяет двум копиям
незаметно разойтись.

## Почему не CSV

Существующий CSV:

- не включает четверти, темы, прогресс по темам и аудит;
- пропускает часть полей экспортируемых сущностей;
- не экранирует запятые и переносы строк;
- импортирует только годы, группы и учеников;
- не имеет номера версии и идентификатора экспорта.

Поэтому CSV оставлен как устаревший обменный формат, но не считается резервной
копией.

## Конверт

```json
{
  "format": "artjournal-backup",
  "formatVersion": 1,
  "exportId": "4bf57251-7b55-4e47-a34f-a69795e1306c",
  "exportedAtEpochMillis": 1785300000000,
  "source": {
    "platform": "android",
    "appVersionName": "1.0",
    "appVersionCode": 1,
    "roomSchemaVersion": 2
  },
  "data": {
    "academicYears": [],
    "groups": [],
    "students": [],
    "payments": [],
    "quarters": [],
    "lessons": [],
    "studentLessonStates": [],
    "topics": [],
    "studentTopicProgress": [],
    "auditLogs": []
  }
}
```

Пример намеренно не содержит персональных данных.

## Правила совместимости

- `format` определяет семейство резервных копий;
- `formatVersion` определяет структуру JSON и изменяется только при
  несовместимом изменении;
- `roomSchemaVersion` описывает исходную локальную схему, но не заменяет
  `formatVersion`;
- `exportId` позволяет серверному импортёру распознать повторную загрузку того
  же файла;
- неизвестная версия формата должна отклоняться до изменения данных;
- дополнительные поля могут игнорироваться совместимым читателем;
- все десять массивов `data` обязательны, даже если они пусты.

В версии v1 значения сущностей сохраняются без нормализации. Например,
`disciplines`, `criteria` и `customFields` остаются строками текущего Room-формата.
Их разбор и преобразование в серверные таблицы выполняет реализованный
импортёр.

## Консистентность

Все таблицы читаются внутри одной Room-транзакции. Это не позволяет получить
backup, в котором часть таблиц снята до пользовательского изменения, а часть —
после него.

Записи сортируются по локальному `id`, чтобы одинаковые данные давали стабильный
порядок массивов. Сам файл при этом не детерминирован: каждый экспорт получает
новые `exportId` и `exportedAtEpochMillis`.

## Контракт серверного импорта

До записи данных сервер:

1. проверяет JSON Schema, `format` и `formatVersion`;
2. вычисляет SHA-256 исходных байтов;
3. валидирует даты, диапазоны, legacy ID и все логические ссылки;
4. строит полный отчёт dry run;
5. только при отсутствии ошибок создаёт предметные записи в одной транзакции.

`exportId` хранится вместе с checksum:

- повтор того же `exportId` и того же checksum не создаёт дубликаты;
- тот же `exportId` с другим содержимым отклоняется как конфликт;
- новый `exportId` считается новой партией импорта.

Последнее правило является осознанным ограничением v1. Каждый новый экспорт
одной Room-базы получает новый `exportId`, поэтому сервер не может надёжно
распознать его как тот же источник. Для более сильной идемпотентности потребуется
стабильный идентификатор источника и новая версия формата.

JWT и серверная матрица доступа уже реализованы, но защищённый import endpoint
пока отсутствует. Поэтому импорт вызывается только через management-команду и
доменный сервис; незащищённый HTTP endpoint намеренно не создаётся.

Пример безопасного dry run через Docker Compose:

```bash
docker compose exec -T web python manage.py import_artjournal_backup \
  /dev/stdin --school SCHOOL_UUID --dry-run < backup.json
```

После успешной проверки уберите `--dry-run`. В этом режиме предметные записи
создаются одной транзакцией, а `ImportBatch` и отчёт сохраняются отдельно.

## Конфиденциальность

Файл содержит ФИО, даты рождения, договоры, посещаемость, оценки, комментарии и
историю оплат. Поэтому:

- backup создаётся через системный выбор файла, а не через clipboard;
- реальные backup-файлы нельзя коммитить в Git или прикладывать к публичным
  issue;
- файл нужно хранить в защищённом месте и удалять после завершения переноса;
- перед передачей разработчику данные должны быть обезличены.

Текущая версия не шифрует содержимое файла и не предоставляет восстановление из
JSON в интерфейсе. Перед использованием приложения с реальными данными нужно
отдельно решить шифрование, политику хранения и безопасный импорт.
