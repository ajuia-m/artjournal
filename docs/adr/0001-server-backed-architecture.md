# ADR-0001: переход к server-backed архитектуре

- Статус: **Accepted**
- Дата: **2026-07-29**
- Уточнено: **2026-07-29** — разделены учебный план, фактический журнал и импорт; изменён порядок этапов
- Область: хранение данных, API, авторизация и синхронизация Android-клиента

## Контекст

Art Journal сейчас является однопользовательским Android-приложением. Room/SQLite на устройстве — единственный источник истины, а ViewModel одновременно отвечает за UI-состояние, бизнес-правила, импорт, отчёты и аудит.

[Зафиксированная текущая модель](../data-model-current.md) подходит для локального прототипа, но не обеспечивает:

- авторизацию и роли преподавателя/администратора;
- совместную работу с одними данными на нескольких устройствах;
- централизованные резервные копии и восстановление;
- внешний и тестируемый API;
- строгую ссылочную целостность и историю переводов ученика;
- надёжные фоновые импорты и формирование отчётов;
- наблюдаемость и единый аудит действий.

Прямое копирование текущих Room-таблиц на сервер закрепило бы сериализованные строки, локальные ID и отсутствующие ограничения. Полная двусторонняя offline-синхронизация на первом этапе, напротив, резко увеличила бы сложность и риск потери данных.

## Решение

Создать server-backed систему в виде модульного монолита:

- **Django** — доменная модель, административный интерфейс и управление приложением;
- **Django REST Framework** — версионированный REST API `/api/v1`;
- **PostgreSQL** — канонический источник истины;
- **JWT access/refresh tokens** — авторизация Android-клиента по HTTPS;
- **Celery + Redis** — только для длительных и повторяемых фоновых задач: импорт, экспорт и формирование отчётов;
- **OpenAPI** — контракт API и основа для клиентских моделей и интеграционных тестов;
- **Kotlin + Jetpack Compose** сохраняются на Android;
- **Room** после миграции становится локальным кешем серверных данных, а не независимым источником истины.

Первый серверный релиз использует online-first запись: изменение считается подтверждённым после ответа API. Офлайн-чтение разрешено из Room. Очередь локальных изменений и разрешение конфликтов не входят в первый этап и потребуют отдельного ADR.

## Граница данных и ролей

Backend вводит явную многопользовательскую область:

- `User` — учётная запись;
- `School` — владелец предметных данных;
- `Membership` — связь пользователя со школой и роль `teacher` или `admin`;
- каждый предметный объект принадлежит школе напрямую либо через родительскую сущность;
- администратор управляет школой, пользователями и справочниками;
- преподаватель работает только с разрешёнными ему группами и журналом.

Точная матрица разрешений зафиксирована в
[документе контроля доступа](../access-control.md). Способ безопасного хранения
токенов на Android будет зафиксирован при подключении клиента. Проверка прав
всегда выполняется на сервере; скрытие элементов UI не считается
авторизацией.

## Модули backend

| Django app | Ответственность |
|---|---|
| `accounts` | Пользователь, JWT-аутентификация, ротация и отзыв refresh-токенов; восстановление доступа добавляется позднее. |
| `schools` | Школы, членства, роли и назначения преподавателей. |
| `education` | Учебные годы, периоды, группы, ученики, календарные исключения и зачисления. |
| `curriculum` | Дисциплины, расписание, темы, критерии и независимые назначения тем группам и учебным периодам. |
| `journal` | Фактически проведённые занятия, пройденные темы, посещаемость, оценки и прогресс учеников. |
| `tuition` | Учёт внесённых оплат за обучение и материалы без интеграции с платёжным провайдером. |
| `imports` | Валидация резервных копий, партии импорта, сопоставление legacy ID и отчёты миграции. |
| `reporting` | Экспорт и генерация отчётов; появляется после основного сценария импорта. |
| `audit` | Неизменяемые серверные события и изолированное хранение импортированной legacy-истории. |

Разделение является границей кода внутри одного deployable-приложения, а не набором микросервисов.

Детальная целевая схема, границы модулей и правила импорта зафиксированы в
[спецификации серверной модели](../server-data-model.md).

## Преобразование модели

| Текущая конструкция Room | Целевая конструкция |
|---|---|
| Локальный `Int` ID | Серверный UUID; при миграции отдельно сохраняется scoped `legacy_local_id`. |
| Нет владельца данных | `School` и `Membership`; все запросы ограничены школой пользователя. |
| `Student.groupId` | `Enrollment(student, group, started_at, ended_at, status)` с историей переводов. |
| `Group.disciplines` | `Subject` и явная связь группы с дисциплиной. |
| `Group.schedule` | `ScheduleEntry` с днём недели, дисциплиной и при необходимости временем. |
| `Quarter` и `quarterMarkers` | Единая сущность учебного периода с типом и границами дат. |
| `Lesson.topicId` | Связь `LessonTopic`: одна тема может занимать несколько занятий, одно занятие может включать несколько тем. |
| `Lesson.isNonSchoolDay` | `CalendarException`; неучебный день не является проведённым занятием. |
| `Topic.criteria` | `TopicCriterion` с порядком и максимальным баллом. |
| `Topic.groupIds`, `Topic.quarterIds` | Независимые `TopicGroupAssignment` и `TopicPeriodAssignment`; отсутствие искусственной пары позволяет назначать тему нескольким группам и периодам. |
| `StudentTopicProgress.criteriaGrades` | Отдельные записи оценки по каждому критерию. |
| `Payment.amount: Double` | `DecimalField`, валюта и явный тип платежа. |
| Даты в `String` | `DateField`; время аудита — timezone-aware `DateTimeField`. |
| `AuditLog` и `revertData` | Импортированная `LegacyAuditEntry`, отделённая от доверенного server audit; отмена — отдельная авторизованная доменная операция. |

Названия таблиц и полный набор полей будут уточнены в миграциях backend, но перечисленные преобразования обязательны.

## Инварианты серверной модели

PostgreSQL и Django должны обеспечивать как минимум:

- существование всех ссылочных объектов через FK;
- не более одного активного учебного года на школу;
- не более одного текущего зачисления ученика;
- единственную запись состояния для пары «ученик — занятие»;
- единственную запись прогресса для пары «ученик — тема»;
- уникальную связь для пары «занятие — тема»;
- границы учебного периода `start_date <= end_date`;
- допустимые диапазоны оценки, прогресса и баллов;
- неотрицательные денежные суммы;
- уникальность роли пользователя внутри школы;
- атомарность операций, которые изменяют несколько связанных записей;
- индексы по школе, группе, ученику, дате занятия и внешним ключам.

Несколько занятий одной группы по одной дисциплине в один день разрешены:
текущий JSON v1 не содержит времени или номера занятия, поэтому сервер не
вводит ложную уникальность по сочетанию даты, группы и дисциплины.

## Контракт Android-клиента

После подключения API Android-клиент разделяется на слои:

1. DTO и API client работают с `/api/v1`.
2. Mapper переводит DTO в локальные cache-модели и обратно.
3. Repository координирует API и Room.
4. Use cases содержат предметные операции.
5. ViewModel отвечает за состояние экрана и вызывает use cases.

Сервер возвращает устойчивые UUID, время изменения и версию/ETag там, где это нужно для обнаружения устаревшего кеша. Только sync/repository слой пишет серверные сущности в Room.

Существующая локальная версия приложения продолжает работать до готовности сквозного серверного сценария. Переключение выполняется контролируемой сборкой или feature flag, а не частичным смешиванием двух источников истины в production.

## Миграция существующих данных

Текущий CSV не является полной резервной копией и не используется как основной миграционный формат.

Перед включением серверного режима необходимо:

1. добавить версионированный полный экспорт всех Room-таблиц в JSON либо другой формат со строгой схемой;
2. включить `exportSchema = true` и добавить явные Room migrations;
3. валидировать даты, диапазоны, сериализованные поля и логические ссылки до отправки;
4. валидировать JSON v1 по машинной JSON Schema до предметной проверки;
5. импортировать данные серверной транзакцией с `import_batch_id` и `legacy_local_id`;
6. хранить `exportId` вместе с SHA-256 исходного файла;
7. сделать повтор одного файла идемпотентным, а совпадение `exportId` при другом checksum считать конфликтом;
8. выполнить dry run и показать ошибки до записи;
9. после импорта сверить количество записей и ключевые агрегаты;
10. сохранить отчёт миграции и спроектировать записи так, чтобы import batch можно было откатить.

Реальные персональные данные учеников не должны попадать в публичный demo, логи CI или тестовые fixtures.

Импорт сначала реализуется как доменный сервис и management-команда. Публичный
HTTP endpoint до появления аутентификации запрещён. Новый экспорт той же
Room-базы получает новый `exportId`, поэтому JSON v1 гарантирует
идемпотентность только для повторной загрузки одного и того же файла. Более
сильная идентификация источника потребует новой версии формата.

## Этапы реализации

### Этап 0. Защита текущих данных

- экспортировать Room schema;
- заменить destructive migration явными миграциями;
- добавить тест полного локального экспорта и восстановления;
- зафиксировать набор анонимизированных fixtures.

### Этап 1. Backend skeleton

- Django/DRF/PostgreSQL в Docker Compose и health checks;
- Pytest, линтеры и CI.

### Этап 2. Серверная модель и безопасный импорт

- минимальные `User` и `School` без публичной аутентификации;
- нормализованная предметная модель и ограничения PostgreSQL;
- JSON Schema v1, dry run и транзакционный идемпотентный импорт;
- management-команда, отчёты импорта и тесты ограничений.

### Этап 3. Авторизация и роли

- `Membership` и роли администратора/преподавателя;
- JWT, OpenAPI и матрица разрешений;
- защищённый API для основного серверного сценария.

Статус этапа: реализованы членства, назначения преподавателей, JWT, blacklist,
матрица и защищённый API управления доступом. OpenAPI и предметный API журнала
остаются следующими вертикальными задачами.

### Этап 4. Подключение Android

- API client, DTO и mapper;
- Room cache;
- авторизация;
- чтение и online-first изменение журнала;
- обработка ошибок и истёкшей сессии.

### Этап 5. Полнота предметной области

- редактирование тем, критериев и расписания через API;
- операции учёта оплат;
- сверка и контролируемое переключение с Room на сервер.

### Этап 6. Фоновые задачи и отчёты

- Celery/Redis;
- экспорт и генерация отчётов;
- журнал ошибок, повтор задач и наблюдаемость.

Offline outbox, автоматическое разрешение конфликтов и sandbox-биллинг могут появиться позднее только после отдельных ADR.

## Последствия

### Положительные

- единый, резервируемый источник истины;
- роли и централизованная проверка доступа;
- строгая целостность и история изменений;
- тестируемый API для Android, QA и будущих клиентов;
- возможность безопасных фоновых задач и отчётов;
- архитектура остаётся достаточно простой для pet-проекта и при этом демонстрирует production-подход.

### Отрицательные и стоимость решения

- появляются backend, PostgreSQL, инфраструктура и эксплуатационные обязанности;
- приложение зависит от сети для подтверждения изменений;
- Android хранит отдельные DTO и cache-модели;
- перенос локальных данных требует отдельного инструмента и тщательной сверки;
- будущая поддержка офлайн-записи потребует версионирования, outbox и политики конфликтов.

## Рассмотренные альтернативы

### Оставить Room единственным хранилищем

Отклонено: не решает роли, совместную работу, централизованный API и резервное копирование.

### Перенести текущую схему в PostgreSQL без нормализации

Отклонено: сериализованные связи, локальные ID и отсутствующие инварианты станут долгосрочным техническим долгом.

### Использовать Firebase или другой BaaS

Отклонено для основной архитектуры: ускоряет отдельные функции, но хуже показывает Python/backend-компетенции проекта и усложняет выражение реляционной предметной модели и серверных транзакций.

### Сразу перейти к микросервисам

Отклонено: независимое масштабирование модулей пока не требуется, а операционная сложность несоразмерна проекту.

### Сразу реализовать полную двустороннюю offline-синхронизацию

Отклонено на первом этапе: конфликтующие изменения и восстановление после частичных ошибок требуют существенно большей модели состояний. Сначала вводятся серверный источник истины и надёжный кеш.

## Не входит в это решение

- настоящий эквайринг и хранение платёжных реквизитов;
- выбор облачного провайдера и production-топология;
- web-клиент для преподавателя;
- точная политика конфликтов офлайн-записи;
- финальная матрица API permissions;
- формат аналитики и уведомлений.

Эти вопросы при необходимости оформляются отдельными ADR.
