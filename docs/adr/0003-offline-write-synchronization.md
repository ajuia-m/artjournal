# ADR-0003: offline-записи и протокол синхронизации

- Статус: **Accepted**
- Дата: **2026-08-01**
- Область: Android Room, WorkManager, Django/DRF, PostgreSQL и transport contract
- Уточняет раздел 5 [ADR-0002](0002-android-server-integration.md)

## Статус реализации в `main`

- ✅ Django app `sync`, `SyncClient`, `SyncCommand`, `ChangeEvent`, версии
  `StudentLessonState`, JSON Schema v1 и runtime-валидация;
- ✅ `POST .../sync/commands/` и `GET .../sync/changes/` с проверкой школы,
  назначений, идемпотентности, `baseVersion`, tombstone и cursor;
- ✅ единый транзакционный write path для REST и sync API;
- ○ snapshot endpoint, retention/compaction и `cursor_expired`;
- ○ синхронизация занятий, прогресса и критериев;
- ○ Android UUID-модель, Room replica/outbox, JWT-клиент, WorkManager и conflict UI.

Таким образом, ADR принят целиком как направление, но в коде завершён только
первый backend vertical slice.

## Контекст

Преподаватель может отмечать посещаемость и оценки в помещении с нестабильной
сетью. Запрет записи без соединения делает журнал ненадёжным именно во время
занятия. При этом простое сохранение HTTP-запросов в файл и их повторная отправка
опасны:

- повтор `POST` после потери ответа может создать дубликат;
- две установки приложения могут изменить одну оценку на разных версиях;
- удаление невозможно корректно передать без tombstone;
- зависимая операция может уйти раньше создания родительской сущности;
- повреждение файла способно потерять всю очередь;
- JWT, membership или teaching assignment могут измениться, пока устройство
  находится без сети.

PostgreSQL остаётся источником подтверждённого состояния. Android должен
позволять локальную работу, сохранять намерения пользователя надёжно и явно
показывать, какие изменения ещё не приняты сервером.

## Решение

### 1. Использовать transactional outbox, а не файл запросов

Очередь хранится в Room-таблице `pending_operations`. В одной транзакции
repository:

1. изменяет локальную рабочую реплику;
2. добавляет неизменяемую операцию в outbox;
3. присваивает локальной записи состояние `pending`.

Если процесс завершится после транзакции, данные и команда сохранятся вместе.
Если транзакция откатится, не останется локального изменения без команды.

Файл допускается только как вручную созданный, зашифрованный диагностический
экспорт. Он не является рабочим хранилищем очереди и не импортируется сервером
как доверенный набор команд.

### 2. Локальная идентичность не зависит от Room `Int`

Каждая синхронизируемая сущность получает UUID до первой серверной отправки.
Один UUID используется в локальной реплике, payload команд и PostgreSQL.
Благодаря этому offline-созданное занятие может быть родителем offline-созданных
состояний учеников без временного сопоставления числовых ID.

Существующие legacy `Int` ID не отправляются как серверная идентичность. Их
перенос выполняется отдельно через JSON v1 и `LegacyObjectMap`.

### 3. Контракт клиентской команды

Каждая операция имеет envelope:

```json
{
  "protocolVersion": 1,
  "operationId": "uuid",
  "clientId": "uuid",
  "clientSequence": 42,
  "schoolId": "uuid",
  "entityType": "student_lesson_state",
  "entityId": "uuid",
  "action": "upsert",
  "baseVersion": 3,
  "dependsOn": [],
  "payload": {},
  "createdAt": "2026-08-01T10:00:00Z"
}
```

Правила:

- `operationId` создаётся один раз и не меняется при повторе;
- `clientId` идентифицирует установку приложения внутри аккаунта;
- `clientSequence` монотонно растёт для упорядочивания команд одного клиента;
- `baseVersion` — последняя подтверждённая версия редактируемой записи;
- создание использует `baseVersion: null`, обновление и удаление — известную
  версию;
- `dependsOn` содержит `operationId` обязательных родительских команд;
- payload имеет типизированную схему для пары `entityType`/`action`;
- хеш канонического envelope сохраняется на сервере. Повтор того же
  `operationId` с другим содержимым возвращает конфликт идемпотентности.

В первой версии `action` ограничен значениями `upsert` и `delete`. Набор
поддерживаемых `entityType` расширяется явно и версионируется.

### 4. Сервер дедуплицирует и проверяет optimistic concurrency

Новый Django app `sync` хранит:

- `SyncClient` — пользователь, установка, время последней активности;
- `SyncCommand` — команда, checksum, статус, сохранённый результат и ошибка;
- `ChangeEvent` — монотонная последовательность изменений школы;
- tombstone в `ChangeEvent` для удалённой сущности.

Уникальность `(school_id, client_id, operation_id)` обеспечивается PostgreSQL.
Обработка одной команды выполняется в `transaction.atomic()`:

1. сервер блокирует или создаёт `SyncCommand`;
2. повтор уже обработанной команды возвращает сохранённый результат;
3. membership, роль и teaching assignment проверяются заново;
4. `baseVersion` сравнивается с текущей версией сущности;
5. domain service применяет изменение и увеличивает `version`;
6. в той же транзакции создаётся `ChangeEvent`;
7. результат и канонический DTO сохраняются в `SyncCommand`.

Запись domain-модели и событие change feed не могут зафиксироваться по
отдельности. Все write paths, включая обычные REST endpoints, должны вызывать
те же application services, чтобы увеличивать версию и создавать событие.

### 5. Sync API

Android использует school-scoped endpoints:

```text
POST /api/v1/schools/{schoolId}/sync/commands/
GET  /api/v1/schools/{schoolId}/sync/changes/?cursor=...
GET  /api/v1/schools/{schoolId}/sync/snapshot/  # planned, not implemented
```

`POST commands` принимает ограниченную пачку, например не более 100 операций и
1 MiB. Результат возвращается для каждой команды независимо:

| Статус | Значение |
|---|---|
| `applied` | команда применена, возвращены canonical payload и новая версия |
| `duplicate` | эта команда уже применялась, возвращён прежний результат |
| `conflict` | `baseVersion` устарела, возвращено текущее состояние сервера |
| `rejected` | нарушены права, схема или предметное ограничение |
| `blocked` | не выполнена операция из `dependsOn` |

HTTP-ошибка описывает отказ всей пачки, например неверный JWT или превышение
лимита. Предметный результат отдельной команды остаётся элементом массива и не
маскируется общим `200 OK` без типизированного статуса.

`GET changes` возвращает события строго после cursor и новый cursor. Cursor
основан на серверной последовательности, а не на часах устройства. После
будущего введения срока хранения change feed клиент должен получать
`cursor_expired` и заново строить подтверждённую реплику через snapshot, не
удаляя локальный outbox. Retention, `cursor_expired` и snapshot пока не
реализованы.

### 6. Android sync engine

В Android добавляются Room-таблицы:

| Таблица | Назначение |
|---|---|
| `pending_operations` | неизменяемые команды и состояния их доставки |
| `sync_metadata` | `clientId`, следующий sequence, cursor и время sync для школы |
| `sync_conflicts` | локальный payload, серверный payload и версии конфликта |

Синхронизируемые локальные записи получают UUID, `serverVersion` и `syncState`.
`syncState` имеет значения `synced`, `pending`, `syncing`, `conflict`,
`rejected`.

`SyncWorker` запускается через WorkManager при наличии сети и:

1. обновляет JWT; при невозможности просит повторный вход и сохраняет outbox;
2. выбирает ограниченную пачку готовых команд в `clientSequence`;
3. отправляет команды и атомарно применяет результаты к Room;
4. загружает change feed от сохранённого cursor;
5. обновляет подтверждённую реплику и cursor одной Room-транзакцией;
6. повторяется, пока есть команды или страницы изменений.

Автоматический retry используется только для transport/5xx с exponential
backoff. `conflict`, `rejected`, `401` после неудачного refresh и постоянные
`4xx` не создают бесконечный цикл.

### 7. Конфликты не сливаются молча

Last-write-wins по времени устройства запрещён для посещаемости, оценок и
платежей. В первой версии конфликт блокирует конкретную операцию и показывает:

- локальное изменение;
- текущее серверное значение;
- автора и время серверного изменения, если политика доступа это позволяет;
- действия «оставить серверное» и «повторить моё поверх новой версии».

Второе действие создаёт **новую** операцию с новым `operationId` и актуальным
`baseVersion`. Исходная конфликтная команда остаётся в журнале как разрешённая.

### 8. Удаления и безопасность

Удаление — версия доменной команды, а не локальное физическое удаление до
подтверждения. Сервер создаёт tombstone event с UUID, типом и версией. Клиенты
удаляют подтверждённую запись после получения события, сохраняя необходимый
audit trail на сервере.

Outbox может содержать персональные данные. Он хранится в приватной базе
приложения; Android backup для него отключается. Решение о SQLCipher или другом
шифровании at rest принимается до пилота с реальными данными. Логи не содержат
JWT, полные payload или заметки преподавателя.

Выход из аккаунта не удаляет неподтверждённые операции молча. Пользователь
должен сначала синхронизировать их, явно экспортировать зашифрованный recovery
bundle либо подтвердить необратимое удаление.

## Изменения в коде

### Android/Kotlin

Статус раздела: **не реализовано**, кроме уже существующей границы
`LocalJournalRepository` и ручного `AppContainer`.

1. Ввести domain-модели с UUID отдельно от legacy Room entities.
2. Добавить Room migration и таблицы outbox, metadata и conflicts.
3. Создать `SyncJournalRepository`; локальную проекцию и outbox менять через
   `RoomDatabase.withTransaction`.
4. Добавить Retrofit/Moshi DTO для commands, results, changes и snapshot.
5. Реализовать защищённую JWT-сессию и single-flight refresh.
6. Добавить `SyncWorker`, connectivity constraints и bounded exponential backoff.
7. Показывать статус sync и отдельный экран разрешения конфликтов.
8. Не отправлять команды непосредственно из ViewModel или Compose.

### Django/DRF/PostgreSQL

Статус раздела: пункты 1–4 и command/change endpoints из пункта 5 реализованы
для `StudentLessonState`. Snapshot, rate limit и retention из пунктов 5–6
остаются следующими задачами.

1. Добавить app `sync`, модели `SyncClient`, `SyncCommand`, `ChangeEvent` и
   constraints идемпотентности.
2. Добавить `version` синхронизируемым aggregate roots и миграции PostgreSQL.
3. Перенести записи journal API из serializer `create/update` в application
   services, которые проверяют версию и создают change event.
4. Реализовать command handlers по белому списку entity/action, не выполнять
   произвольные имена моделей из payload.
5. Добавить batch commands, cursor changes и snapshot endpoints в OpenAPI.
6. Ограничить размер пачки, payload, rate и срок хранения command results.
7. Повторно использовать текущую school/role/assignment матрицу доступа.

### Transport contract

1. Добавить JSON Schema для protocol v1 и fixtures совместимости Kotlin/Python.
2. Зафиксировать enum типов, статусов и кодов ошибок.
3. Канонизировать JSON перед SHA-256 для защиты `operationId` от подмены.
4. Не полагаться на часы клиента для порядка и разрешения конфликтов.
5. Версионировать sync protocol независимо от формата backup JSON v1.

## Этапы реализации

1. Общий protocol schema, UUID и server versions.
2. Backend command log, один handler для `StudentLessonState`, change feed и тесты.
3. Android outbox/worker для посещаемости и оценок, включая перезапуск процесса.
4. Conflict UI и сценарий отзыва membership.
5. Занятия и зависимые команды, затем progress/criterion scores.
6. Snapshot recovery, нагрузочные ограничения и полный offline/online E2E.

Каждый этап оформляется отдельным PR. Нельзя одновременно переносить все десять
legacy-сущностей: такой diff будет плохо проверяем и затруднит поиск потери данных.

## Обязательные тесты

- локальная запись и outbox фиксируются или откатываются вместе;
- перезапуск процесса не теряет pending operation;
- один `operationId` при повторе применяется сервером ровно один раз;
- тот же `operationId` с другим checksum отклоняется;
- устаревший `baseVersion` возвращает conflict и не меняет domain row;
- зависимая команда блокируется при отказе родительской;
- tombstone доходит до второго клиента;
- отозванная membership отклоняет накопленные команды;
- истёкший cursor восстанавливается через snapshot без потери outbox;
- offline → несколько изменений → reconnect → restart сходится с PostgreSQL;
- две установки, изменившие одну оценку, получают воспроизводимый конфликт.

## Последствия

### Положительные

- преподаватель может работать во время нестабильной сети;
- повтор запроса не создаёт двойную операцию;
- конфликт не затирает оценку молча;
- локальная очередь переживает перезапуск приложения;
- sync protocol отделён от backup/import.

### Отрицательные

- объём Android и backend первого интегрированного релиза заметно увеличивается;
- Room перестаёт быть простым cache и требует миграций и sync-состояний;
- все серверные write paths должны использовать общий application service;
- потребуется отдельный UX pending/rejected/conflict;
- отладка нескольких устройств сложнее обычного CRUD API.

## Отклонённые альтернативы

### Файл будущих HTTP-запросов

Отклонено как основное хранилище: нет удобных транзакций с локальными данными,
индексов, блокировок, частичного подтверждения и безопасной конкурентной записи.

### Повтор обычных `POST`/`PATCH` после появления сети

Отклонено без `operationId` и `baseVersion`: повтор может создать дубль, а
устаревший `PATCH` — затереть изменение другого преподавателя.

### Last-write-wins по `updatedAt`

Отклонено: часы устройств ненадёжны, а молчаливое затирание оценок и
посещаемости неприемлемо.

### CRDT и автоматическое полевое слияние

Отклонено для первой версии как чрезмерно сложное. Явный optimistic conflict
даёт предсказуемое поведение и оставляет возможность добавить безопасные
domain-specific merge rules позднее.

## Не входит в первую версию

- произвольное редактирование всех десяти legacy-таблиц без сети;
- peer-to-peer синхронизация устройств;
- CRDT и автоматическое объединение конфликтующих оценок;
- синхронизация бинарных вложений;
- использование JSON backup v1 как очереди операций.
