# ADR-0002: поэтапное подключение Android к server-backed режиму

- Статус: **Accepted**
- Дата: **2026-08-01**
- Область: Android data layer, авторизация, миграция локальных данных и поведение без сети
- Заменяет уточнения об Android cache из ADR-0001 там, где этот документ задаёт более узкие правила первого клиентского релиза
- Поведение offline-записей из раздела 5 уточнено в [ADR-0003](0003-offline-write-synchronization.md)

## Контекст

В репозитории существуют две рабочие, но пока не соединённые системы:

- Android-приложение хранит десять типов сущностей в Room/SQLite, использует
  локальные `Int` ID и уже обращается к Room через `LocalJournalRepository` и
  ручной `AppContainer`, но ещё не имеет сетевой реализации repository;
- Django/DRF backend хранит нормализованную модель в PostgreSQL, использует
  серверные UUID, JWT, школы, роли и проверку доступа к каждой операции.

Backend уже поддерживает занятия, связи занятия с несколькими темами и состояния
ученика на занятии. Android по-прежнему работает без сетевых запросов. Обход
repository boundary прямыми Retrofit-вызовами из ViewModel создал бы два
источника истины и не определил бы, какая версия записи должна победить после
ошибки, повторного запроса или работы на другом устройстве.

Разрешение offline-записей без дополнительного протокола небезопасно. Для него
нужны обязательные механизмы:

- стабильных клиентских UUID для существующих Room-записей;
- журнала локальных изменений и tombstone-записей для удалений;
- версии серверной записи или другого протокола optimistic concurrency;
- идемпотентных ключей для повторяемых клиентских команд;
- политики разрешения конфликтов и восстановления после частичной ошибки.

ADR-0003 принимает эти механизмы как обязательную часть интеграции, а не как
неопределённую будущую доработку.

JSON v1 решает перенос одного снимка, но не синхронизацию. Повтор одного файла
идемпотентен по `exportId` и SHA-256, однако новый экспорт той же Room-базы
получает новый `exportId`. Сервер не может доказать, что это обновлённый снимок
того же источника, и вправе считать его новой партией.

## Решение

### 1. Сервер является источником истины в server-backed режиме

Первый интегрированный Android-клиент работает **server-authoritative с
offline-записями**:

- пользователь может локально создать или изменить поддерживаемую сущность без
  сети, но такая операция имеет видимый статус `pending`, а не считается
  подтверждённой сервером;
- локальное изменение и запись команды в outbox выполняются одной Room-транзакцией;
- после восстановления сети WorkManager отправляет ту же команду с постоянным
  `operationId`, не создавая новый запрос при каждом повторе;
- окончательный статус, права, допустимые переходы и предметные ограничения
  определяет backend;
- конфликт версии и отклонённая операция видимы пользователю и не заменяются
  скрытым last-write-wins.

### 2. Локальный и серверный режимы не смешиваются

До завершения миграции приложение поддерживает два явно различимых режима:

| Режим | Источник истины | Допустимые записи |
|---|---|---|
| `Local legacy` | текущая Room-база | только через существующий локальный репозиторий |
| `Server workspace` | PostgreSQL через `/api/v1` | локально через Room outbox с последующим подтверждением API |

Один экран или use case не должен одновременно объединять предметные данные
Room и API. Переключение режима является явным действием пользователя после
входа, выбора школы и, при необходимости, завершённого импорта. Feature flag
может скрывать незавершённый server-backed режим, но не менять источник данных
внутри уже открытой сессии.

В `Server workspace` Room является **рабочей локальной репликой**: подтверждённую
часть можно восстановить из API, а неподтверждённый outbox нельзя удалять до
получения результата сервера или явного решения пользователя. UI обязан
различать подтверждённые данные, ожидающие операции и конфликты.

### 3. Android получает явную границу данных

Подключение выполняется через следующие зависимости:

```text
Compose UI -> ViewModel -> use case -> repository interface
                                      |-> local legacy repository -> Room
                                      `-> sync repository -> Room replica + outbox
                                                            `-> WorkManager -> API
```

- Compose и ViewModel не создают Room, Retrofit или token storage напрямую;
- сетевые DTO, Room entities и доменные модели остаются разными типами;
- mapper явно преобразует UUID, даты, nullable-поля и серверные enum;
- выбранный режим определяет одну реализацию repository на время сессии;
- ошибки сети, авторизации, прав, валидации и конфликта представлены разными
  состояниями, а не одной строкой `Exception.message`.

В server-backed режиме идентичностью предметной записи является серверный UUID.
Новые UI-модели и navigation arguments не должны предполагать, что идентификатор
всегда является `Int`. Существующие локальные `Int` ID остаются деталью legacy
repository и не отправляются как серверные идентификаторы.

### 4. Сессия и школа выбираются явно

Android-клиент должен:

1. получить access/refresh tokens через существующий JWT endpoint;
2. хранить refresh token в защищённом хранилище с ключом Android Keystore;
3. держать access token в памяти либо в хранилище с тем же уровнем защиты;
4. выполнять единственное согласованное обновление токена при параллельных `401`;
5. завершать сессию, если refresh отклонён или отозван;
6. загрузить доступные школы и потребовать явный выбор рабочей школы;
7. никогда не считать выбранную в UI роль доказательством доступа.

Идентификатор школы задаёт клиентский контекст запросов, но backend повторно
выводит школу из защищённого объекта и проверяет membership/assignment.

### 5. Без сети разрешены чтение и очередь поддерживаемых изменений

Клиент показывает последнюю локальную реплику с отметкой времени синхронизации.
Создание и изменение поддерживаемых сущностей разрешено: приложение атомарно
обновляет локальное представление и добавляет команду в Room outbox.

После появления сети клиент обновляет JWT, отправляет ограниченную пачку команд
в порядке `clientSequence`, получает канонические данные сервера и затем
забирает изменения других клиентов по серверному cursor. Неопределённый сетевой
результат приводит к повтору **той же** команды с тем же `operationId`.

Удаление передаётся tombstone-командой. Конфликт `baseVersion` не разрешается
автоматически: сервер возвращает актуальную версию, а клиент показывает
пользователю выбор между отменой локального изменения и осознанным повтором на
новой базе. Полный контракт, статусы и границы первой версии определяет
[ADR-0003](0003-offline-write-synchronization.md).

### 6. JSON v1 используется как одноразовая миграция

Переход существующего пользователя выполняется контролируемо:

1. Android создаёт полный JSON v1;
2. защищённый school-scoped endpoint выполняет dry run;
3. пользователь видит ошибки, предупреждения и количества сущностей;
4. тот же файл импортируется транзакционно;
5. клиент сверяет успешный `ImportBatch` и основные количества;
6. только после явного подтверждения открывается server workspace.

Новый экспорт v1 нельзя использовать как инкрементальное обновление уже
мигрировавшей школы. Повторный импорт с новым `exportId` блокируется продуктовым
сценарием, пока оператор явно не выберет отдельную новую миграцию.

Если потребуется повторяемая синхронизация снимков, формат v2 должен добавить
стабильный `sourceInstanceId`, стабильные UUID объектов, `updatedAt`, удаления и
однозначные правила upsert. Эти поля не следует неявно добавлять в v1.

## Этапы реализации

### Этап A. Архитектурная граница Android

- выделить repository interfaces и use cases для серверного сценария;
- оставить существующий Room-код за `local` implementation;
- ввести доменные идентификаторы, не зависящие от Room `Int`;
- покрыть выбор реализации unit-тестами.

### Этап B. Авторизация и рабочая школа

- API client и единый error mapper;
- login, refresh и logout;
- защищённое хранение refresh token;
- список доступных школ и выбор активной школы;
- тесты истёкшей и отозванной сессии.

### Этап C. Server-backed журнал и offline write foundation

- сначала чтение групп, учеников, занятий и состояний;
- затем стабильные UUID, Room replica, outbox, sync metadata и WorkManager;
- серверные версии, идемпотентный command log, change feed и tombstone;
- создание занятия и изменение посещаемости, оценки и домашней работы через
  единый sync protocol;
- Compose UI-тесты loading/offline/pending/conflict/forbidden состояний.

До завершения этапа требуется закрыть серверный API прогресса по зачётным темам
и оценок по критериям, если эти функции входят в переключаемый экран.

### Этап D. Миграция

- защищённый endpoint поверх существующего import service;
- лимит файла и таймаут;
- dry run и структурированный отчёт;
- подтверждённое переключение local legacy -> server workspace.

### Этап E. Сквозная проверка

- поднять Django и PostgreSQL в Docker Compose;
- войти из Android-клиента тестовым пользователем;
- создать занятие и состояние ученика;
- перезапустить клиент и подтвердить данные повторным чтением;
- проверить отказ для чужой школы и отозванного refresh token.

## Последствия

### Положительные

- в каждой сессии существует один определённый источник истины;
- offline-команды безопасно переживают перезапуск и неопределённый сетевой ответ;
- локальный прототип продолжает работать до готовности всего сквозного пути;
- ошибки импорта, сети и конфликты не превращаются в скрытые частичные изменения;
- изменения с разных устройств сходятся через серверный cursor и версии.

### Отрицательные

- sync protocol, server change log и UI конфликтов существенно увеличивают объём первого релиза;
- локальный и серверный режимы временно требуют двух реализаций repository;
- UI и ViewModel придётся отвязать от числовых Room ID;
- JSON v1 подходит только для контролируемого переноса, а не для регулярной
  синхронизации;
- не все сущности обязаны поддерживать offline-запись в первой версии.

## Отклонённые альтернативы

### Немедленно заменить Room прямыми Retrofit-вызовами из ViewModel

Отклонено: смешивает UI, сессию, transport и предметные операции, затрудняет
тестирование и оставляет неявное поведение при переключении источника данных.

### Считать Room и PostgreSQL равноправными источниками истины

Отклонено: без версий, tombstone и протокола конфликтов это приводит к
перезаписи более новых данных и неразрешимым дублям.

### Использовать JSON v1 для периодической синхронизации

Отклонено: новый экспорт получает новый `exportId`, а локальные ID не являются
глобальной стабильной идентичностью источника.

### Считать локальное изменение окончательно успешным до ответа сервера

Отклонено: пользователь может потерять доступ к школе, нарушить предметное
ограничение или изменить устаревшую версию. Локальная операция остаётся
`pending`, пока сервер не вернёт `applied`, `duplicate`, `conflict` или `rejected`.

## Не входит в это решение

- регистрация, подтверждение email, восстановление пароля и MFA;
- production hosting и push-уведомления;
- автоматическое полевое слияние конфликтующих оценок и посещаемости;
- синхронизация произвольных legacy Room-сущностей без стабильных UUID;
- фоновые импорты через Celery;
- web-клиент и настоящий платёжный провайдер.
